# Findings useful for the Shopware core

This list holds findings from the proof of concept that matter for the Shopware core, independent of PostgreSQL support: bugs or weak spots on MySQL/MariaDB today, cleanups that lower the cost of supporting more databases, and performance ideas that help every database.
Each entry links its source doc. New waves add their findings here (rule in each wave's `_shared.md`).

Kinds: **bug** (wrong or arbitrary result on MySQL/MariaDB today), **robustness**, **portability** (needed for any second database, harmless on MySQL), **performance**.

| # | Kind | Finding | Where | Suggestion for core | Source |
|---|---|---|---|---|---|
| 1 | bug | A grouped query sorts by `LENGTH(col)` on a column that is not aggregated. On MySQL that uses an arbitrary row's value. | `CriteriaQueryBuilder`, natural sorting in a query with a group by (admin `property-group-option` search) | Use `LENGTH(MIN(col))` / `LENGTH(MAX(col))` when the query has a group by. The PoC does this on every platform. | docs/06 (table near the end) |
| 2 | robustness | The DAL depends on `ONLY_FULL_GROUP_BY` being off: `MySQLFactory` removes it from the session `sql_mode`. The DAL groups by `id` when a to-many join is involved but selects other columns too. For versioned entities the key is `(id, version_id)`, so even root columns are not functionally dependent. | `MySQLFactory`, `EntityReader::fetch()`, `EntitySearcher::search()` | Make the selects valid under strict grouping (group by the full key, or aggregate; the PoC wraps them in `any_value()` on PostgreSQL via `makeSelectValidForGroupBy()`) and then stop changing `sql_mode`. | docs/06, item 1 |
| 3 | robustness | `HAVING _score >= :_minScore` refers to a select alias, and the `EntityAggregator` score subquery groups by an unqualified `id`. Both only work because MySQL is lenient. | `CriteriaQueryBuilder`, `EntityAggregator` | Repeat the expression in `HAVING` and qualify the column. The PoC does this on every platform. | docs/06, items 2 and 3 |
| 4 | robustness | `StatesUpdater` relies on a `LEFT JOIN` with a partial `GROUP BY`. | `Content/Product/DataAbstractionLayer/StatesUpdater.php` | Use `EXISTS`, as in the PoC. | docs/06 |
| 5 | robustness | Code catches failed statements and continues inside the same transaction (unique violation in the context persister, `SET FOREIGN_KEY_CHECKS`, ...). This works on MySQL, but breaks on any database that aborts the transaction on error. | context persister and others, see docs/09 | Use savepoints around statements that are expected to fail, or check before writing. | docs/09 |
| 6 | robustness | The DAL counts rows per partition with MySQL session variables (`@n:=IF(@c=..., @n+1, ...)` and `SET @n = 0, @c = null`). MySQL 8 deprecates setting user variables inside expressions. Both supported minimums (MySQL 8.0.22, MariaDB 10.11, `DatabaseConnectionFactory`) support `ROW_NUMBER() OVER (PARTITION BY ...)`. | `EntityReader` (to-many limit per parent) | Use the window function on every database. The PoC already has it as `SqlDialect::rowNumberPerPartition()` for PostgreSQL and SQLite. | code, docs/summary.md |
| 7 | portability | 715 id columns are `binary(16)`. 309 files outside migrations converted ids between hex and bytes by hand. | whole core | Keep hex ids above the connection and bind them in one place (`IdBinding` in the PoC, used in 313 files, mostly rewritten with a Rector rule). | docs/15, docs/20 |
| 8 | portability | 446 files use the connection and 241 contain MySQL-specific SQL. 910 migrations are MySQL DDL. Extensions write raw MySQL. | whole core | A `SqlDialect` service (upsert, JSON, group concat, quoting, case-insensitive compare) for core and extensions, and a database-neutral migration API for new migrations. | docs/01, docs/04, docs/10 |
| 9 | performance | The storefront product detail read is one statement with 19 joins: the parent self-join, 9 eagerly loaded to-one associations and 9 translation subqueries. On PostgreSQL its planning costs 5 ms warm and 15-48 ms cold. On MariaDB parse and optimize stay below 3 ms, but the statement is still wide. | `EntityReader`, product detail criteria | Wave 6 A: with the plan cache (`DATABASE_PLAN_CACHE`) the planning left is 7.4 ms (generic) or 13.3 ms (auto) per detail request, so splitting the statement for planning reasons is not worth it. | docs/18 cause 4, docs/22, `benchmark-results/wave5-statements/storefront-product-detail.json` |
| 10 | performance | Parallel product writes deadlock on shared `product` rows: indexer bulk `UPDATE product` statements (inheritance, categories, category tree, cheapest price) run against the writer and against each other. MariaDB detects deadlocks at once; PostgreSQL waits `deadlock_timeout`, which turns them into a 10x throughput loss. | `ProductIndexer` and updaters | Wave 6 B: lock the written products, their children and their parents once in id order (`SELECT ... ORDER BY id FOR UPDATE`) before the indexer updaters run, PostgreSQL only; 0 deadlocks (45 before). Core-wide the better fix is one fixed row order in the updaters themselves (bulk `UPDATE` statements run in plan order, `ProductCategoryDenormalizer` and `CheapestPriceUpdater` loop per product). | docs/19 |
| 11 | performance | Persistent connections are off by default. PostgreSQL pays about 40 ms per request for a new backend; MySQL pays about 1 ms to connect. | connection setup, `.env` template | Wave 6 A: ICU costs 8.8 ms once per backend and connect 5.6 ms; use `DATABASE_PERSISTENT_CONNECTION=1` plus `DATABASE_PLAN_CACHE=1` for PostgreSQL (docs/22). | docs/18 cause 3, docs/22, docs/13 |
| 12 | robustness | A multi-row `INSERT ... ON DUPLICATE KEY UPDATE` with two rows of the same key works on MySQL (the rows are applied one after the other, the last row wins for the update columns). `MultiInsertQueue` callers rely on that without saying so, and every standard-conform upsert (`ON CONFLICT DO UPDATE`, SQL `MERGE`) rejects it. | `MultiInsertQueryQueue::addUpdateFieldOnDuplicateKey()` and its callers | Merge rows with the same key in the queue (first row kept, update columns from the last row) and document the rule. The PoC does this for PostgreSQL only through `SqlDialect::upsertCollisionColumns()`. | docs/21, section "Wave 6" |
| 13 | robustness | Price accessor results depend on two MySQL details. The cash rounding division `ROUND(x * m, 0) / m` returns scale 4 because of `div_precision_increment`, and the tests assert the string `'50.0000'`. The currency factor is applied to a DOUBLE (`text + 0.0`), so `13.016666666666666 * 1.5` rounds up to 19.525 where exact decimal arithmetic gives 19.52499... | `PriceFieldAccessorBuilder`, `EntityAggregatorTest`, `PriceFieldTest::testCashRoundingFilter` | Make scale and arithmetic explicit (`CAST(... AS DECIMAL(x, 4))`, a documented choice between double and decimal for the factor). The PoC keeps the MySQL behaviour through `SqlDialect::decimalDivisionScale()` and `castToFloat()`. | docs/21, section "Wave 6" |
| 14 | robustness | `ORDER BY col DESC` relies on MySQL sorting NULL as the smallest value (first for ASC, last for DESC); the DAL never states a NULL order. `EntityAggregatorTest::testTermsAggregationWithSorting` expects the NULL bucket last. PostgreSQL does the opposite (`NULLS FIRST` for DESC). It also changes which products a sorted search returns: the admin product search sorted by `name ASC` returns the 25 NULL-name variants first on MariaDB and named products on PostgreSQL (834 of 1916 `product_translation` rows of the catalog data set have a NULL name). `EntityReader` cuts the last four characters of an order part to get the direction, which breaks as soon as a NULL placement is added. | `CriteriaQueryBuilder::addSortings()`, `EntityAggregator::addSorting()` | Decide and document the NULL order of `FieldSorting` and state it in the SQL (`NULLS FIRST` / `NULLS LAST` or an `IS NULL` sort key), so that every database returns the same order. | docs/21, section "Wave 6", docs/23 |
| 15 | portability | Test code compares `HEX(id)` (upper case on MySQL) with lower case hex ids and only passes because the MySQL collation is case-insensitive (`TreeIndexerTest::testIndexTree`). The `UPDATE` silently matches nothing on a case-sensitive database. | tests that use `HEX(id) IN (:ids)` | Bind the ids (`id IN (:ids)` with the id binding) instead of comparing hex text. | docs/21, section "Wave 6" |
| 16 | performance | DBAL's pdo_pgsql driver sets `PGSQL_ATTR_DISABLE_PREPARES`, so every DAL statement is parsed and planned again on PostgreSQL, 64-85 plans per storefront request (11-25 ms planning). Server-side prepared statements per persistent connection remove 63-95 % of that. | DBAL pdo_pgsql driver options, connection factory | Prepare per backend and SQL text (`PlanCacheMiddleware`), only with persistent connections. | docs/22 |
| 17 | performance | The `ci` collation of PostgreSQL (nondeterministic ICU) makes `LIKE` and sorts on string columns slow: `prefix` 224 ms and `contains` 1567 ms on 500 000 rows (sequential scan), against 57 and 62 ms with `lower(col) COLLATE ucs_basic`, 6.3 and 7.6 ms with an expression btree or trigram index. A plain btree on a `ci` column serves only `=`. The cost is the database's collation, MySQL does not have it. | `SqlQueryParser` string filters | Case-insensitive but accent-sensitive filters through `lower(col) COLLATE ucs_basic` plus expression indexes on the columns that are looked up by value. | docs/23 |
| 18 | robustness | Search results depend on the accent-insensitive MySQL collation: a filter for `muller` matches `Müller` on MySQL and MariaDB (`utf8mb4_unicode_ci`, `utf8mb4_0900_ai_ci`) but not on SQLite or on PostgreSQL after the faster `lower()` form. No test and no documentation states which of the two is intended. | `SqlQueryParser` (`equals`, `equalsAny`, `contains`, `prefix`, `suffix`), DAL docs | State the intended behaviour (accent-insensitive search is a MySQL collation side effect) and cover it with a test. | docs/23 |
| 19 | performance | Once the DAL states MySQL's NULL order on every sort (row 14), a sort column needs an index declared with that order to serve `ORDER BY ... LIMIT` on a database whose default order differs. Checked on PostgreSQL with the 39 distinct statements the 7 benchmark scenarios send: only the admin product list sorted by product number loses an index scan (9.2 ms against 6.0 ms per page on 1840 products); an index `(product_number NULLS FIRST, version_id)` runs it in 0.1 ms. Most DAL sorts (translation names, positions, stock) are sorted in memory on both variants. | `CriteriaQueryBuilder` sort building, `product` indexes | Declare sort indexes of hot admin list columns with the NULL order the DAL emits, or add them only where a listing sorts large tables with `LIMIT`. | [docs/13](13-benchmark.md) "Rerun after wave 6", [docs/02](02-decisions.md) |
| 23 | performance | The search keyword filter `lower(keyword) = :term OR lower(keyword) LIKE '%term%'` on `product_search_keyword` scans the whole table in every statement that carries the keyword score (about seven per search request). A trigram index serves the leading wildcard on PostgreSQL (0.1 ms instead of 8.4 ms per statement on 34k rows); MySQL has no equivalent index type, so a precomputed scored-ids result per request would help every database. | `ProductSearchBuilder`, `EntityAggregator` score subquery, `product_search_keyword` | [docs/25](25-postgresql-search-and-detail.md) |
| 24 | idea | Each aggregation of the search page repeats the whole keyword score subquery. One scored-ids subselect or temporary result per request would run it once. Idea, not measured. | `EntityAggregator`, `CriteriaQueryBuilder` | [docs/25](25-postgresql-search-and-detail.md) |
