# Switch test: the same code on MySQL 8, MariaDB and PostgreSQL (wave 3, handoff A)

Question: does the same code install and run from scratch on each database, and how long does a switch take?
Method as in "Switch test" in `docs/11-database-comparison.md`.

## What was run

`scripts/switch-db.sh mysql|mariadb|postgresql` (smoke checks in `scripts/switch-smoke.py`).
Per run, against an empty database `shopware_switch` (the lane database `shopware` is not touched):

1. `bin/console system:install --basic-setup --drop-database --create-database --force` (910 migrations).
2. PostgreSQL only: apply `mysql-compat.sql` (the core does not load it yet, known gap).
3. `framework:demodata --reset-defaults --products 200 --categories 20 --manufacturers 10 --properties 10 --customers 10 --orders 10 --tags 20 --rules 10 --promotions 3 --newsletter-recipients 5 --reviews 10 --media 100`.
4. `dal:refresh:index`, `cache:clear`.
5. Second web process (`php -S`, own port, own `APP_CACHE_DIR`) inside `instance-web-1`, then the smoke test: storefront home, category listing and search, admin token, admin product search, product create and update through the admin API with read back, sync API upsert and delete, store API guest registration, add to cart and order.

Setup and container details are in `docs/03-environment.md` ("Switch test databases").
Everything runs with `APP_ENV=prod` (`framework:demodata` requires it).

Environment: MySQL 8.4.13, MariaDB 10.11.16, PostgreSQL 18.7, all in containers without resource limits on the same Podman VM (8 CPUs, 16 GB), PHP 8.4.17.
Code: branch `poc/db-independent`, `instance/` HEAD `c20c6e630ae` plus uncommitted work of the parallel sessions in the working tree.
Raw numbers of every run: `docs/switch-results/<db>.tsv`.

## Result

Three runs per database, all steps passed in all nine runs.
Seconds, median of three (single runs in brackets).

| Step | MySQL 8 | MariaDB | PostgreSQL |
|---|---|---|---|
| `system:install` (910 migrations, basic setup) | 31.8 (27.7 / 42.7 / 31.8) | 16.6 (16.6 / 17.8 / 13.0) | 15.5 (20.7 / 15.5 / 11.7) |
| `framework:demodata` | 10.0 (10.0 / 10.7 / 8.4) | 8.1 (8.1 / 8.8 / 7.6) | 12.3 (14.5 / 12.3 / 9.0) |
| `dal:refresh:index` | 5.1 (5.1 / 5.6 / 4.2) | 3.2 (3.9 / 2.8 / 3.2) | 7.1 (7.1 / 7.5 / 4.4) |
| `cache:clear` | 1.9 | 1.9 | 2.3 |
| Storefront home | 0.6 | 0.5 | 0.7 |
| Storefront listing | 0.2 | 0.3 | 0.5 |
| Storefront search | 0.1 | 0.1 | 0.2 |
| Admin token | 0.6 | 0.6 | 0.7 |
| Admin product write (create, update, read) | 0.2 | 0.2 | 0.3 |
| Sync API | 0.0 | 0.0 | 0.1 |
| Store API checkout (register, cart, order) | 0.4 | 0.4 | 0.7 |
| Total, install to end of smoke test | 49.6 (48.0 / 66.0 / 49.6) | 34.4 (34.4 / 34.9 / 29.0) | 42.4 (49.8 / 42.4 / 32.0) |

How to read the numbers:

- The runs are not a benchmark: other sessions used the same machine and edited the checkout at the same time, the spread between runs is large (MySQL install 27.7 to 42.7 s).
- Demo data is random (variants, property options), so the product count differs per run (about 320 to 460 products), which affects demodata and indexing time.
- The storefront steps are the first requests against a cold cache of the new process.
- The switch itself, from an empty database to a working shop with demo data, takes about 35 to 50 seconds on every database.

## Failures

No step failed in the final runs on any database.
Failures that came up while building the harness:

| Where | Failure | Cause | Resolution |
|---|---|---|---|
| all | `framework:demodata`: `Cannot get N elements, only M in array` (Faker) | the generator needs at least 3 product download media (`i % 30 === 0` of the media count) and enough tags, rules, properties, manufacturers; small counts fail randomly | counts raised (media 100, tags 20, ...), not a regression |
| all | `Key cannot be empty` in the JWT configuration, then `dev` environment instead of `prod` | `php -S` does not put environment variables into `$_SERVER` (`variables_order=GPCS`), Symfony runtime reads `$_SERVER` | web process started with `-d variables_order=EGPCS` |
| all | install, demodata or index crashed with `Class ...Dbal\SqlDialectFactory not found`, `Argument #7 ($dialect) must be of type ...Dbal\SqlDialect`, `QueryBuilder::select(): Argument #1 must be of type string, array given` | uncommitted, half finished edits of handoffs C and E in the shared working tree at that moment | gone once those sessions finished the edit, not present in committed code (checked `git show HEAD:` for the persister) |
| PostgreSQL | `function rand() does not exist` (demodata, `ORDER BY RAND()`) | `mysql-compat.sql` has no `rand()` | `rand()` added to `mysql-compat.sql` (commit `c2d1f6bc413`) |
| PostgreSQL | `dal:refresh:index`: `mysql_compat_to_bool(EXCLUDED."is_deleted";)` syntax error | `MultiInsertQueryQueue` appends `;` to the upsert generated by the PostgreSQL dialect (since `cbcca5e236f`), the boolean rewriter put the `;` inside the last expression | `BooleanAssignmentRewriter` keeps a trailing terminator outside (commit `a0489af0cd8`, unit test added) |

There was no failure on MySQL 8 or MariaDB that is a regression of the PoC branch against trunk.

## Open points

- `mysql-compat.sql` is still applied by the harness, not by `system:install` on PostgreSQL. A clean install on PostgreSQL needs that step until the core loads it.
- The smoke test covers the paths named in the plan, not the admin UI, flows over the message queue or the search index (OpenSearch is not part of the lane).
- SQLite is not part of the harness yet (handoff D).
